# Author an animation

Work from the Animation Engine repo root. Read `AGENTS.md`, `docs/scene-format.md` and `docs/animation-library.md`. Use English for content and communication unless the user explicitly requests another language, even when their prompt is in Swedish.

## Select the project

1. Run `npm run --silent engine -- library list`. Use the stable animation ID as the primary reference in prompts and delivery; titles are descriptive. Match an existing animation by ID, falling back to its title when needed. Ask only if multiple matches make the target ambiguous.
2. For an update, retrieve the latest revision with `library get <id> --out .cache/<unique-name>.scene.json`. The output path must not already exist. Record the returned revision number. Preserve existing node, connection and step IDs.
3. For a new animation, choose a descriptive lowercase ID and a unique working scene file under `.cache/`. Read an example as a schema reference; do not overwrite examples. For a requested variant, copy the existing scene into a new project ID.

## Build the explanation

1. Infer a short sequence of teaching steps, audience, pacing and takeaway. Default to a calm 15–60 second, 1080p30 explanation. Save the brief and explanation plan to `output/<id>/plan.md`. Proceed without an approval checkpoint unless critical factual ambiguity blocks progress.
2. Search the existing SVG library using `npm run --silent engine -- assets <terms> [--collection personal|aws|downloads]`. Use returned IDs in node `icon` fields. Prefer existing assets and generic built-in shapes.
3. Write only scene JSON for ordinary animation work. Do not edit the engine, preview, composition registration or default scene to create another video. Preserve unaffected content when revising. For overall micro-scene pacing, use its numeric `speed` (default 1, range 0.1–8): `2` is twice as fast, `0.45` slower. This scales events and holds in preview and export; change individual base durations only when requested. Recheck the total clip length after retiming.
4. Supported events: `show`, `hide`, `draw`, `focus`, `send` (including `reverse`), `camera` and `status`. Events run sequentially; targets within one event act together. Use at most four columns, preferably two nodes per column, and short labels/captions. The schema limits clips to 60 seconds. Dashed arrows, groups, moving nodes, obstacle routing and arbitrary simultaneous events are not implemented. Explain a material limitation; do not silently invent unsupported fields or claim an approximation implements the missing feature. Engine work requires a request for that capability.
5. Scene `theme` supports `paper`, `midnight`, `rose-pine` and `dawn`; default new animations to `rose-pine` and preserve explicit themes on revisions unless asked to change style. Give every authored `send`, including replies, a meaningful `label` (up to 28 characters) unless the user explicitly requests an unlabelled flow. Name the operation or payload, such as `GET /products`, `Code + verifier` or `Product data`; avoid generic `Request`/`Response` when more specific text is known. Never invent protocol details just to fill a label. The schema keeps labels optional for older scenes, but missing labels produce `MISSING_MESSAGE_LABEL` warnings. Add labels to new or changed sends; for narrowly scoped revisions, report untouched unlabelled messages instead of expanding the edit. A send can also use either a built-in `symbol` (`envelope`, `key`, `token`, `document`, `check`, `error`) or catalog `icon`, never both. Icons supplement text. Send/arrival effects default to `pulse`; set `effects: "none"` for plain travel. See `examples/message-styles.scene.json`. Review labels near endpoints for overlaps and allow enough reading time.

End new animations on a readable full-architecture overview unless the user requests another ending: show all relevant nodes, draw their connections, reset the camera with empty targets, clear temporary status badges, and hold the settled overview for about 2–3 seconds. Inspect the final frame. On narrow edits, preserve unrelated history and report any missing overview rather than silently expanding scope.

## Validate, inspect, save and deliver

For directed shots, use `camera` with node IDs; `targets: []` returns to overview. Frame both message endpoints, let the camera settle before sending, and keep the number of shots purposeful. `zoom` caps magnification; the engine fits components and labels. Other components fade out during the shot. Prefer `labelPosition: "travel"` so request text moves with the symbol. Use `anchored` only when requested or needed for readability. `reading: {before: 0.3, after: 0.5}` adds reading pauses inside the send duration. Leave at least 0.1 seconds for travel. `status` events set a persistent text/tone badge on nodes; `text: null` clears it. Place processing states after request arrival and results after the relevant check. Do not imply real latency, progress or certification. Camera/status events add time; step speed scales everything. Read `docs/scene-format.md` for exact fields and review camera transitions, message phases and status wording before delivery.

1. Run `npm run --silent engine -- validate .cache/<working>.scene.json --json`. Fix diagnostics. Allow up to three automatic repair attempts; if still blocked, keep the draft and report the concrete problem.
2. Export representative PNGs with `frame <scene> --at <seconds> --out output/<id>/review-<step>.png`. Inspect them for readable text, direction, overlaps and explanation accuracy. For changes to motion or timing, also inspect playback or frames during the changed motion. Valid JSON is not visual approval.
3. Save through `library save <id> <scene> --expected-revision <N> --note "Describe the change"`. Use N=0 for a new project. Never directly edit `animations/*.animation.json`. On a conflict, fetch the latest revision and reapply only the intended changes; never force an overwrite.
4. Before delivering a finished animation, follow `skills/architecture-review/SKILL.md` for the source-backed technical review and any necessary repairs. That skill uses the same review method as the studio button. Retain the final reviewed revision R for export. A review-only request belongs to that skill and does not authorize changing the animation.
5. Use `review check <id> --revision R` before final export, then `render @<id> --revision R --require-review --out output/<id>/rR/video.mp4`. Missing, stale, incorrect or unverified reviews block this export. If unresolved, preserve the draft and explain the specific problem; never mark it reviewed just to pass the gate. Rendering is deterministic and needs no model once a report exists. If export fails, report that the project is saved but video export is incomplete.
6. Start `npm run dev` if needed, or use the already running studio. Link `http://127.0.0.1:<port>/?animation=<id>`, the video, and the scene. The **Architecture review** button runs the same research task through local Codex CLI and shows feedback for the selected saved revision. Do not start duplicate servers on occupied ports. Save a brief visual verification report in `output/<id>/rR/review.md`; technical reports live in `reviews/`. Never claim a check was performed when it was not.

For a restore, `library restore <id> --revision <old> --expected-revision <current>` creates a new revision and preserves history. Routine revision requests follow the same validation, inspection and export workflow.

The browser is a library/player with text, theme, message and step-speed controls, plus an Architecture review button. The coding agent supplies AI authoring; the button uses local Codex CLI with live research to review a saved scene. It does not edit the scene or connect to a deployed environment.
